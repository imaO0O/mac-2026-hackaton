# МАС «Нефтекод»: АВТ → гидроочистка → блендинг

Мультиагентная система, которая по состоянию процесса оценивает риск выхода за
спецификацию, сравнивает допустимые изменения режима и выдаёт оператору
объяснимую рекомендацию — либо мотивированно отказывается её давать.

Жёсткое правило системы: **качество и технологические ограничения выше экономики**.
Недопустимый режим нельзя компенсировать производительностью.

## Быстрый старт

```bash
git clone https://github.com/imaO0O/mac-2026-hackaton.git
cd mac-2026-hackaton
python -m venv .venv && .venv\Scripts\activate     # Windows
pip install -r requirements.txt
pip install -e .
```

Пути к данным — через переменные окружения (файлы в git не хранятся):

```bash
copy .env.example .env
set NEFTE_SOURCE_DIR=C:/путь/к/выдаче        # где лежат xlsx, pdf, data.rar
set NEFTE_DATA_DIR=C:/путь/к/локальным/данным # куда распаковать csv (НЕ в OneDrive)
```

Подготовка данных (распаковка архива + parquet-кэш, ~2 минуты, один раз):

```bash
python scripts/prepare_data.py
```

Проверка:

```bash
pytest -q
python scripts/run_cycle.py --ts "2026-04-20 12:00"
```

Ожидаемый вывод последней команды — отказ от рекомендации: «Установка остановлена:
нет расхода сырья и реактор холодный». В эти же сутки поточный анализатор серы
завис на 18.4 мг/кг, но это следствие останова, а не отдельная поломка: через
прибор ничего не идёт. Система обязана назвать оператору причину, а не следствие.
Умение корректно отказаться — часть требований ТЗ.

Обучение агента качества (CPU, ~3 минуты) — без него система работает на
персистенции, с ним подключается виртуальный анализатор:

```bash
python scripts/train_quality.py --horizon 0                 # виртуальный анализатор
python scripts/train_quality.py --horizon 2 --no-monotone   # прогноз на 2 часа
```

Флаг `--no-monotone` во второй команде не косметика: именно с ним получен
закоммиченный `reports/quality_metrics_h2.json`, и без него отчёт не
воспроизводится. На горизонте 2 часа монотонные ограничения по физике модели
мешают — связи «режим → сера через два часа» в данных нет, и ограничение только
сужает её без пользы.

Бэктест агента надёжности и отчёт по достоверности данных (CPU, ~1 минута):

```bash
python scripts/backtest_reliability.py
```

Дашборд оператора (локально, CPU, без интернета):

```bash
streamlit run app/dashboard.py
```

Рецептура смешения на заданный момент (в цикле она считается сама, этот скрипт —
разбор блока по частям):

```bash
python scripts/run_blending.py --ts "2026-02-28 00:00" --additive 500
```

Жёсткая проверка: «злые» кейсы, тестовый период, замкнутый контур и сравнение
архитектур (CPU):

```bash
python scripts/check_adversarial.py       # порченые данные: система обязана отказаться
python scripts/run_test_period.py         # весь 2026 год: исходы и пропуски
python scripts/run_simulation.py          # что будет, если оператор послушается
python scripts/compare_architectures.py   # зачем нужен каждый агент — в числах
```

Нейросетевые модели (нужна NVIDIA и отдельно поставленный torch, см.
`docs/GPU_SETUP.md`; в демо не обязательны):

```bash
python scripts/train_sequence.py --arch tcn --window 48 --pretrain  # анализатор серы
python scripts/train_anomaly_ae.py                                  # аномалии режима
python scripts/run_cycle.py --model seq --anomaly ae                # подключить в цикл
```

Сценарий защиты одной командой — пять сцен, в каждой сказано, что показывать:

```bash
python scripts/demo.py            # весь сценарий, ~3 минуты
python scripts/demo.py --list     # какие сцены есть
```

Отдельные окна, если нужно копнуть:

```bash
python scripts/run_cycle.py --window stable --every 20D                # устойчивый режим
python scripts/run_cycle.py --window quality_risk --every 10D          # риск по качеству
python scripts/run_cycle.py --window bad_data_frozen_pak --every 2D    # недостоверные данные
```

Каждый прогон пишется в `reports/runs/<timestamp>.json`: входной срез, ответы всех
агентов, итоговая рекомендация — чтобы логику решения можно было проверить.

## Как устроен один цикл

1. `StateBuilder.build(ts)` собирает срез: телеметрия обеих установок, последние
   ЛИМС и ПАК **вместе с возрастом**, флаги достоверности.
2. `QualityAgent` выбирает источник по приоритету ЛИМС → ПАК → ВАК, прогнозирует
   серу на горизонт и оценивает вероятность выхода за 10 мг/кг.
3. `ReliabilityAgent` считает тяжесть режима по прокси (WABT, ΔP Р-202, печь) и
   сужает диапазоны уставок.
4. `OptimizerAgent` генерирует варианты внутри модельных диапазонов, **отсекает
   недопустимые до ранжирования**, ранжирует свёрткой и по Парето.
5. `BlendingAgent` считает рецептуру товарного ДТ **на прогнозной сере выбранного
   варианта** и проверяет сумму долей = 100 %.
6. `Orchestrator` выбирает итог: удержать режим, изменить уставки или отказаться —
   и объясняет решение.

## Текущее состояние

* **Агент качества — рабочий.** Виртуальный анализатор на CatBoost: MAE 1.37 мг/кг
  на тесте против 1.48 у поточного анализатора, ROC-AUC риска 0.80, покрытие
  интервала 0.89 — ровно то, что воспроизводит `scripts/train_quality.py --horizon 0`
  (`reports/quality_metrics_h0.json`). Признаки режима реактора и монотонные
  ограничения по физике — `docs/REGIME_FEATURES.md`, метрики и ограничения —
  `docs/QUALITY_AGENT.md`. Использованный источник качества агент называет сам
  (ЛИМС → ПАК → ВАК), и при недостоверных приборах помечает значение как ВАК со
  сниженной уверенностью, а не выдаёт его за измерение.
* **Отклик на уставки даёт гибридный суррогат:** уровень серы берётся у модели,
  приращение считается по кинетике гидрообессеривания. Без него подъём температуры
  на 2 °C менял прогноз на 0.008 мг/кг, с ним — на 3.2, и оптимизатору стало из
  чего выбирать.
* **Агент надёжности — рабочий.** Детекторы достоверности переведены в код,
  severity нормируется строго по обучающему периоду, бэктест показал обратную
  связь тяжести режима с превышениями по сере (AUC 0.35 на тесте) — то есть
  конфликт целей подтверждён числом. Добавлены наработка катализатора, многомерный
  детектор аномалий и пороги risk_class из квантилей обучающего периода.
* **Останов установки распознаётся отдельно.** 20 эпизодов (3.9 % времени), где
  реактор холодный и сырья нет, раньше принимались за отказ датчиков — и система
  советовала остановленной установке поднять температуру. Этим же объясняются
  54 % «зависаний поточного анализатора»: через прибор ничего не идёт.
  Подробности — `docs/RELIABILITY_AGENT.md`.
* **Агент оптимизации и оркестратор — рабочие.** Поиск в три слоя (бездействие,
  покоординатная сетка, комбинации с локальным уточнением), прозрачные прокси
  выпуска и энергозатрат, фронт Парето, лимит частоты воздействий и два уровня
  допустимости: «с гарантированным запасом» и «улучшает, но без гарантии».
  Чувствительность к весам свёртки измерена: при разбросе ±50 % решение
  «вмешиваться или нет» сохраняется в 100 % случаев, а вот величина воздействия
  гуляет на 1.90 °C и прогноз серы на 2.34 мг/кг — вдвое больше, чем запас до предела.
  Поэтому оператору показывается фронт Парето и альтернативы, а не единственный
  «оптимальный» вариант.
  Подробности — `docs/OPTIMIZER_AGENT.md`.
* **Блок смешения — рабочий и встроен в цикл.** Данных по компонентам в пакете не
  выдано, поэтому модель построена на явных допущениях. Рецептура считается внутри
  оркестратора на **прогнозной** сере выбранного варианта и попадает в
  `Recommendation.blend`; проверка суммы долей = 100 % стоит в списке проверенных
  ограничений. Главный вывод: прямогонную фракцию под Евро-5 подмешать нельзя
  (предельная доля 0.013 %), единственный рычаг по сере — глубина гидроочистки.
  Подробности — `docs/BLENDING.md`.
* **Жёсткая проверка пройдена.** Восемь «злых» кейсов с заранее записанными
  ожиданиями (`scripts/check_adversarial.py`) и полный прогон по тестовому
  периоду 2026 года (`scripts/run_test_period.py`). Кейсы нашли три настоящие
  ошибки — скачок сырья был невидим для агента надёжности, в карточке оператора
  показывался источник качества, которого в решении не было, а при недостоверных
  приборах система работала «как обычно». Все три исправлены, разбор и результаты
  прогона — `docs/HARD_CHECKS.md`.
* **Нейросети проверены и не приняты.** TCN/GRU на окне телеметрии (в том числе с
  предобучением на 265 тыс. показаний поточного анализатора) выигрывают у бустинга
  на валидации во всех пяти конфигурациях и проигрывают на тесте во всех пяти:
  MAE 1.54–1.69 против 1.30, покрытие интервала падает с 0.85 до 0.61–0.66.
  LSTM-автоэнкодер аномалий уступает расстоянию Махаланобиса на единственном
  событии, где есть сигнал (зависание анализатора: лифт 2.0 против 3.7), и теряет
  объяснимость. Отдельно проверен прогноз на 2 часа — самое слабое место системы:
  сеть выиграла валидацию у бустинга по обоим показателям и получила на тесте
  ROC-AUC 0.42, хуже монетки. Предупреждать заранее в этих данных нечем, и это
  теперь измерено, а не предположено. Обе модели подключаются в цикл флагами `--model seq` и
  `--anomaly ae` — контракт подключения проверен на работающих моделях, а не
  описан на словах. Числа и разбор — `docs/GPU_MODELS.md`.
* **Обзор пути принятия решения нашёл одиннадцать дефектов**, и это оказалось
  результативнее внешних проверок. Главные: тяжесть режима была одинаковой у всех
  вариантов, из-за чего четвёртый критерий оптимизации не работал вовсе; риск
  варианта был флагом 0/1; уверенность всегда равнялась 0.95, то есть в карточке
  стояло украшение. Плюс тихие ошибки — кэш признаков, не зависящий от настроек,
  утечка при отборе колонок, смесь с неизвестной серой, считавшаяся нулевой. Все
  закрыты тестами, разбор — `docs/HARD_CHECKS.md` §5. Второй заход добавил ещё
  шесть: одна и та же секунда истории давала РАЗНУЮ рекомендацию при повторном
  прогоне (генератор случайных чисел жил в агенте), карточка молчала о том, что
  последний анализ уже вне спецификации, а три «различающиеся» альтернативы
  отличались в третьем знаке. На метрику решений всё это почти не повлияло
  (пропуски 41 → 40 из 65), и так и должно быть: правки про корректность, а не
  про числа.
* **Имитационная среда с замкнутым контуром** (`scripts/run_simulation.py`):
  рекомендации применяются, процесс отвечает, система видит последствия своего
  совета. С первого запуска нашла главное: система упирала режим в предел
  допустимого дрейфа — каждый шаг не больше 2 °C и проходит все проверки, а
  последовательность уводит установку в упор. Исправлено насыщением запаса по
  качеству и подавлением воздействия; движение уставок за полгода упало с 227 до
  43 °C при тех же пропусках и ложных тревогах.
* **Сравнение архитектур в числах** (`scripts/compare_architectures.py`) — ответ
  на вопрос «зачем вам четыре агента». Одноагентная система двигает уставки в 21
  раз больше и при этом пропускает БОЛЬШЕ превышений (66 % против 58 %). Агент
  надёжности не ловит превышений вовсе — он экономит треть нагрузки на
  оборудование при том же качестве. Разбор — `docs/HARD_CHECKS.md` §6–7.
* Что делать дальше — `docs/PLAN.md`.
