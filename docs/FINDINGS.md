# Что сделано и что нашли

Рабочий журнал проекта, который раньше жил в README: все команды, структура кода,
состояние каждого агента и история находок — с тем, что проверили и сняли. Витрина
решения — `README.md`; здесь подробности, на которые она ссылается.

Числа этого документа сверяются с отчётами тестами
(`tests/test_readme_matches_reports.py`, `tests/test_docs_match_reports.py`).

## Все команды

Обучение агента качества (CPU, ~3 минуты) — без него система работает на
персистенции, с ним подключается виртуальный анализатор:

```bash
python scripts/train_quality.py --horizon 0                 # виртуальный анализатор
python scripts/train_quality.py --horizon 2                 # прогноз на 2 часа
python scripts/train_quality.py --target t95 --horizon 0    # второй показатель
```

Раньше вторая команда требовала флага `--no-monotone`, и это объяснялось тем, что
на горизонте 2 часа монотонные ограничения по физике модели мешают. Объяснение
оказалось неверным: мешал дефект в самих ограничениях — с ними CatBoost терял
начальное приближение и недотягивал до уровня цели. После исправления физика
помогает на всех горизонтах, флаг больше не нужен и остался только как инструмент
проверки. Разбор — `docs/REGIME_FEATURES.md`, тесты — `tests/test_monotone_offset.py`.

Бэктест агента надёжности и отчёт по достоверности данных (CPU, ~1 минута):

```bash
python scripts/backtest_reliability.py
```

Дашборд оператора (локально, CPU, без интернета):

```bash
streamlit run app/dashboard.py
```

Рецептура смешения на заданный момент (в цикле она считается сама, этот скрипт —
разбор блока по частям):

```bash
python scripts/run_blending.py --ts "2026-02-28 00:00" --additive 500
python scripts/run_blend_scenarios.py     # десять сценариев «а если»
```

Разбор данных под ответы организаторов:

```bash
python scripts/check_calibration.py       # честна ли вероятность, по которой решают
python scripts/check_drift.py             # стареет ли модель и когда переобучать
python scripts/check_vak_against_lims.py  # формулы справочника против лаборатории
python scripts/check_feature_stability.py # устойчив ли отбор признаков к сиду
python scripts/check_t95_sigma.py         # разброс Т95 как функция возраста анализа
python scripts/check_alarm_budget.py --horizon 2 --model seq --arch tcn --window 48 --pretrain
                                          # держится ли бюджет тревог и что даёт скользящий порог
python scripts/check_run_safety.py train_quality.py  # заденут ли правки идущий прогон
python scripts/check_cetane.py            # цетановое число: тренд, индекс, цена присадки
python scripts/find_delays.py             # запаздывание «уставка → сера» по данным
python scripts/check_tag_meaning.py       # что теги измеряют на самом деле (24-2000)
python scripts/check_avt_formulas.py      # то же для АВТ: сверка формул с лабораторией
python scripts/check_avt_schemes.py       # схемы АВТ с кодами тегов против КИП и балансов
python scripts/check_pipeline_point.py    # какая точка ЛИМС стоит за «Pipeline» в формулах ВАК
python scripts/check_kinetic_order.py     # что, если сера отвечает на температуру слабее
python scripts/check_catalyst_life.py     # дезактивация катализатора и остаток цикла
python scripts/check_catalyst_life.py --checkpoint-day 150   # контрольная точка
```

Последние две команды закрывают критерий «надёжность оборудования» числами:
катализатор теряет **0.85 °C/мес** активности (95 % ДИ [0.71, 0.98]), до уровня,
с которого установку выводили раньше, осталось 16.6 °C, то есть **13–20 месяцев,
ближе к 17** (`docs/CATALYST_LIFE.md`). Сама оценка проверена бэктестом на цикле,
исход которого известен: на той же наработке она промахнулась на +11 %, а к концу
цикла врёт вдвое — поэтому во второй половине цикла показывать её нельзя. А четыре формулы справочника, которые «не
воспроизводятся на выданных тегах», оказались не проблемой тегов: три из них —
ошибки записи, названные поимённо (`docs/AVT_TAGS.md`).

Жёсткая проверка: «злые» кейсы, тестовый период, замкнутый контур и сравнение
архитектур (CPU):

```bash
python scripts/check_adversarial.py       # порченые данные: система обязана отказаться
python scripts/run_test_period.py         # весь 2026 год: исходы и пропуски
python scripts/run_simulation.py          # что будет, если оператор послушается
python scripts/compare_architectures.py   # зачем нужен каждый агент — в числах
python scripts/train_quality.py --horizon 0 --no-vak   # абляция формул справочника
```

Нейросетевые модели (нужна NVIDIA и отдельно поставленный torch, см.
`docs/GPU_SETUP.md`; в демо не обязательны):

```bash
python scripts/train_sequence.py --arch tcn --window 48 --pretrain  # анализатор серы
python scripts/train_anomaly_ae.py                                  # аномалии режима, 3 сида
python scripts/run_cycle.py --model seq --anomaly ae                # подключить в цикл
```

Сценарий защиты одной командой — пять сцен, в каждой сказано, что показывать:

```bash
python scripts/demo.py            # весь сценарий, ~3 минуты
python scripts/demo.py --list     # какие сцены есть
```

Отдельные окна, если нужно копнуть:

```bash
python scripts/run_cycle.py --window stable --every 20D                # устойчивый режим
python scripts/run_cycle.py --window quality_risk --every 10D          # риск по качеству
python scripts/run_cycle.py --window bad_data_frozen_pak --every 2D    # недостоверные данные
```

Каждый прогон пишется в `reports/runs/<timestamp>.json`: входной срез, ответы всех
агентов, итоговая рекомендация — чтобы логику решения можно было проверить.

## Как устроен один цикл

1. `StateBuilder.build(ts)` собирает срез: телеметрия обеих установок, последние
   ЛИМС и ПАК **вместе с возрастом**, флаги достоверности.
2. `QualityAgent` выбирает источник по приоритету ЛИМС → ПАК → ВАК, прогнозирует
   серу на горизонт и оценивает вероятность выхода за 10 мг/кг.
3. `ReliabilityAgent` считает тяжесть режима по прокси (WABT, ΔP Р-202, печь) и
   сужает диапазоны уставок.
4. `OptimizerAgent` генерирует варианты внутри модельных диапазонов, **отсекает
   недопустимые до ранжирования**, ранжирует свёрткой и по Парето.
5. `BlendingAgent` считает рецептуру товарного ДТ **на прогнозной сере выбранного
   варианта** и проверяет сумму долей = 100 %.
6. `Orchestrator` выбирает итог: удержать режим, изменить уставки или отказаться —
   и объясняет решение.

Правила оркестратора, в порядке проверки: установка стоит → отказ; данные
недостоверны или уверенность ниже порога → отказ; ни один вариант не проходит
жёсткие ограничения → отказ с перечнем причин; действие было недавно (запрет
частых воздействий) → ждём; риск ниже порога и текущий режим допустим → держим;
иначе — лучший допустимый вариант. Выключателями в конфиге добавляются возврат к
базовому режиму, робастная гарантия и ожидание при повторе с неизменным риском.

**Путь решения — часть рекомендации** (`Recommendation.trace`): что вернул каждый
агент и какое правило сработало. Его показывает дашборд («Цикл решения: кто что
сказал»), пишет журнал цикла `reports/runs/*.json` и возвращает сервис.

**Цикл как служба.** `python -m nefte.service` — локальный HTTP-сервис на
стандартной библиотеке: `GET /health`, `GET /decide?ts=…`, `POST /decide` со срезом
`ProcessState`, `POST /ask` — вопрос оператора. Граница интеграции с системой сбора
данных — контракт `ProcessState`. Ограничение: модель качества берёт признаки из
матрицы по времени, поэтому для среза вне истории работает персистенция.

**Необязательный слой локальной LLM** (`src/nefte/llm_explain.py`, выключен).
Отвечает на вопрос оператора через OpenAI-совместимый API модели сети предприятия.
Модели передаётся только структура решения; ответ, в котором есть число не из неё,
отклоняется, и оператор видит объяснение системы с пометкой.

## Что сделано и что нашли, по частям

* **Агент качества — рабочий и двухпоказательный.** Виртуальный анализатор на
  CatBoost: MAE 1.29 мг/кг на тесте против 1.48 у поточного анализатора, ROC-AUC
  риска 0.82, покрытие интервала 0.82, полнота тревоги 0.72 против 0.36 у ПАК —
  ровно то, что воспроизводит `scripts/train_quality.py --horizon 0`
  (`reports/quality_metrics_h0.json`). Обучены все четыре горизонта из
  заявленного организаторами диапазона 0–3 ч. Про уровень (MAE) модель бьёт
  поточный анализатор на всех четырёх, и разрыв растёт; на нулевом горизонте,
  по парному бутстрэпу, разница на границе значимости (−0.19 мг/кг, интервал до
  +0.003), дальше — значима. А вот РАЗЛИЧЕНИЕ превышений дальше нулевого горизонта
  измерить не удалось: ROC-AUC гуляет от 0.40 до 0.69 на часовом горизонте при
  смене одного лишь сида отбора признаков, а по трём независимым пересборкам
  матрицы — 0.46 → 0.71 → 0.40. Все главные числа — с 90 % интервалами — в
  `docs/QUALITY_AGENT.md`, что из них говорить на защите — `docs/DEFENSE_QUALITY.md`. Честный ответ здесь — «не знаем», а не
  «не работает». Нулевой горизонт в тех же трёх сборках стоит как вкопанный (0.82,
  0.81, 0.82), то есть заголовочные числа подтверждены: проверка отличает
  горизонт, где сигнал есть, от горизонта, где его нет.
  `scripts/check_feature_stability.py`. Признаки режима реактора и монотонные
  ограничения по физике — `docs/REGIME_FEATURES.md`, метрики и ограничения —
  `docs/QUALITY_AGENT.md`. Использованный источник качества агент называет сам
  (ЛИМС → ПАК → ВАК), и при недостоверных приборах помечает значение как ВАК со
  сниженной уверенностью, а не выдаёт его за измерение.
* **Отклик на уставки даёт гибридный суррогат:** уровень серы берётся у модели,
  приращение считается по кинетике гидрообессеривания. Без него подъём температуры
  на 2 °C менял прогноз на 0.008 мг/кг, с ним — на 3.2, и оптимизатору стало из
  чего выбирать.
* **Агент надёжности — рабочий.** Детекторы достоверности переведены в код,
  severity нормируется строго по обучающему периоду, бэктест показал обратную
  связь тяжести режима с превышениями по сере (AUC 0.35 на тесте) — то есть
  конфликт целей подтверждён числом. Добавлены наработка катализатора, многомерный
  детектор аномалий и пороги risk_class из квантилей обучающего периода.
* **Останов установки распознаётся отдельно.** 20 эпизодов (3.9 % времени), где
  реактор холодный и сырья нет, раньше принимались за отказ датчиков — и система
  советовала остановленной установке поднять температуру. Этим же объясняются
  54 % «зависаний поточного анализатора»: через прибор ничего не идёт.
  Подробности — `docs/RELIABILITY_AGENT.md`.
* **Агент оптимизации и оркестратор — рабочие.** Поиск в три слоя (бездействие,
  покоординатная сетка, комбинации с локальным уточнением), прозрачные прокси
  выпуска и энергозатрат, фронт Парето, лимит частоты воздействий и два уровня
  допустимости: «с гарантированным запасом» и «улучшает, но без гарантии».
  Чувствительность к весам свёртки измерена на 40 моментах (14 из них с
  действием): при разбросе ±50 % решение «вмешиваться или нет» сохраняется в
  100 % случаев, величина воздействия гуляет на 0.45 °C, прогноз серы на
  0.10 мг/кг, а вот НАПРАВЛЕНИЕ воздействия от весов зависит в каждом четвёртом
  моменте. Поэтому оператору показывается фронт Парето и альтернативы, а не
  единственный «оптимальный» вариант: спорят не величины, спорит выбор ручки.
  Прежние числа в этой строке (1.90 °C и 2.34 мг/кг) были средним по ОДНОМУ
  моменту с действием из десяти — разбор в `docs/OPTIMIZER_AGENT.md`.
  Подробности — `docs/OPTIMIZER_AGENT.md`.
* **Т95 — второе жёсткое ограничение, и оно не декоративное.** Исправленная
  формула виртуального анализатора даёт Т95 с коэффициентом 0.50 по температуре
  Р-202: каждые +2 °C ради серы поднимают Т95 на градус при запасе до предела в
  пять. Уровень берётся из лаборатории, приращение — из формулы, потому что у
  формулы MAE 5.5 °C и жёсткий предел по её абсолютному значению был бы ложной
  точностью. Замкнутый прогон показал цену: на июньском окне пять вмешательств
  убирают все четыре шага с превышением серы, а к Т95 добавляют **+0.08 °C в
  среднем** (худший сдвиг 0.16). Числа прежней версии этой строки («6 % времени →
  0 %», +0.12 °C) посчитаны на имитации, которая не показывала системе последствий
  её действий, — разбор в `docs/HARD_CHECKS.md` §10. Стоявшее здесь ещё раньше
  «доля времени выше предела Т95 растёт с 12 % до
  26 %» было артефактом: оценка Т95 со смещениями была пустой в 71 шаге из 175
  (формула не переносила отбракованные расходы газа 24-2000, которые вариант даже не
  трогает), и доли считались по разным шагам. На одних и тех же шагах — 12 % против
  15 %, и вся разница — шесть шагов, где исторический Т95 ровно 360.0. Тот же
  дефект молча выключал ограничение по Т95 в 11 % моментов теста; исправлен,
  решения в тесте не изменились.
* **Одна найденная связь исправила три места сразу.** Т95 зависит от температуры
  Р-202, а её никто не задаёт уставкой: оптимизатор двигает T5 и T11, T6 —
  следствие. Пока связь не была измерена, проверка Т95 давала ровно нулевой вклад
  во всех точках имитации. Связь померили — ΔT6 = 0.72·ΔT5 + 0.18·ΔT11, R² = 0.63
  на 126 753 отсчётах, — и оказалось, что та же T6 занижала ещё два расчёта:
  тяжесть режима и признаки суррогата качества, оба примерно на 40 %. Метод
  полезнее самой находки: **обнаружив, что величина не пересчитывается, надо сразу
  искать все места, где она участвует.**
* **Блок смешения — рабочий и встроен в цикл.** Данных по компонентам в пакете не
  выдано, поэтому модель построена на явных допущениях. Рецептура считается внутри
  оркестратора на **прогнозной** сере выбранного варианта и попадает в
  `Recommendation.blend`; проверка суммы долей = 100 % стоит в списке проверенных
  ограничений. Главный вывод: прямогонную фракцию под Евро-5 подмешать нельзя
  (предельная доля 0.013 %), единственный рычаг по сере — глубина гидроочистки.
  Организаторы назвали обязательными три показателя — серу, Т95 и цетановое
  число, — и все три теперь проверяются: рецептура оптимизируется по выпуску ЗА
  ВЫЧЕТОМ стоимости цетаноповышающей присадки, а не по голому выпуску. Несколько
  нежёстких сценариев — `scripts/run_blend_scenarios.py`.
  Подробности — `docs/BLENDING.md`.
* **Цетановое число падает, и это нашлось в данных.** 55.9 (2023) → 54.5 → 53.2 →
  52.3 (2026), последний анализ 21.07.2026 — **50.0 при нормативе 51**. Показатель
  меряют раз в месяц, классический цетановый индекс ASTM D976 на этих данных не
  работает (корреляция с лабораторией 0.03 — хуже, чем просто среднее), поэтому
  прогноза цетанового числа у нас нет и мы его не выдумываем: оно входит как
  ограничение по последнему анализу с поправкой на измеренный тренд. Единственный
  быстрый рычаг — присадка, которая по цене организаторов в 100 раз дороже
  топлива: закрыть текущую нехватку в 1 единицу стоит 2.1 % цены тонны.
  Разбор — `python scripts/check_cetane.py`.
* **Запаздывание «уставка → сера» измерено, а не взято с потолка.** Организаторы
  назвали диапазон 0–3 ч и просили найти эмпирически. Взаимная корреляция первых
  разностей на поточном анализаторе (122 тыс. отсчётов, только train, остановы и
  залипший прибор выкинуты) даёт **чистое запаздывание меньше 10 минут** — на
  сетке данных неразличимо — и **постоянную времени канала 4.6 ч**. Знак реакции у
  всех семи управляющих тегов совпал с физикой: рост температуры снижает серу.
  У двух тегов связь «сера раньше уставки» сильнее обратной — это контур
  оператора, и мы об этом говорим прямо. `python scripts/find_delays.py`.
* **Жёсткая проверка пройдена.** Восемь «злых» кейсов с заранее записанными
  ожиданиями (`scripts/check_adversarial.py`) и полный прогон по тестовому
  периоду 2026 года (`scripts/run_test_period.py`). Кейсы нашли три настоящие
  ошибки — скачок сырья был невидим для агента надёжности, в карточке оператора
  показывался источник качества, которого в решении не было, а при недостоверных
  приборах система работала «как обычно». Все три исправлены, разбор и результаты
  прогона — `docs/HARD_CHECKS.md`.
* **Нейросети проверены; на nowcast не приняты, на раннем предупреждении — да.** TCN/GRU на окне телеметрии (в том числе с
  предобучением на 265 тыс. показаний поточного анализатора) ПРОИГРЫВАЮТ бустингу
  на тесте во всех пяти конфигурациях и по всем трём показателям:
  ROC-AUC 0.52–0.77 против 0.82 и покрытие интервала 0.63–0.76 против 0.82. По MAE
  оговорка обязательна: 1.29–1.76 против 1.289, то есть **лучшая из сетей (GRU-48)
  даёт 1.292 — ничья**, а не проигрыш. Разрыв держится на двух других показателях.
  Раньше сети хотя бы выигрывали валидацию по MAE — после исправления утечки ЛИМС,
  формул справочника и смещения от монотонных ограничений перестали и это.
  LSTM-автоэнкодер аномалий уступает расстоянию Махаланобиса на единственном
  событии, где есть сигнал (зависание анализатора: лифт 2.0 против 3.7), и теряет
  объяснимость. **Прогноз на 2 часа сеть закрыла наполовину.** На уровне метрик
  сигнал есть: ROC-AUC 0.67–0.72 на трёх тройках сидов; у бустинга на пяти сидах
  0.41–0.66 (медиана 0.47) — выше 0.5 только один сид из пяти. Прежнее «против
  0.41» было сравнением с худшим из них.
  На уровне решений — три сида у обеих моделей: при 40–50 % ложных тревог худший
  сид сети пропускает меньше лучшего сида бустинга, а на той строгости, при
  которой система работает (25–30 % ложных), диапазоны перекрываются (сеть 65–83 %,
  бустинг 71–78 %), и по парному бутстрэпу по неделям ни один сид сети там от
  бустинга не отличим. Сам бустинг на уровне решений устойчивее сети в 2–3 раза, но
  его рабочий сид — лучший из трёх: «69 % пропусков» — число удачного сида. И сама
  мера «по моментам» зависит от шага прогона: при реальной частоте раз в час у той
  же системы 84 %, а по лабораторным пробам система в окне от двух часов до отбора
  до публикации результата реагирует на 83 % проб с превышением против 49 %
  нормальных; за сутки вперёд не предупреждает (`docs/HARD_CHECKS.md`). Стоявшее здесь
  «49 % против 71 %» снято: проверка устойчивости по сидам затирала основную
  модель, и какая модель тогда отработала, восстановить нельзя (дефект исправлен,
  отчёт прогона теперь называет артефакт). Собственная рабочая точка сети даёт
  77–83 % ложных тревог, и она тянет torch в демо. Обе модели подключаются в цикл флагами `--model seq` и
  `--anomaly ae` — контракт подключения проверен на работающих моделях, а не
  описан на словах. Числа и разбор — `docs/GPU_MODELS.md`.
* **Обзор пути принятия решения нашёл одиннадцать дефектов**, и это оказалось
  результативнее внешних проверок. Главные: тяжесть режима была одинаковой у всех
  вариантов, из-за чего четвёртый критерий оптимизации не работал вовсе; риск
  варианта был флагом 0/1; уверенность всегда равнялась 0.95, то есть в карточке
  стояло украшение. Плюс тихие ошибки — кэш признаков, не зависящий от настроек,
  утечка при отборе колонок, смесь с неизвестной серой, считавшаяся нулевой. Все
  закрыты тестами, разбор — `docs/HARD_CHECKS.md` §5. Второй заход добавил ещё
  шесть: одна и та же секунда истории давала РАЗНУЮ рекомендацию при повторном
  прогоне (генератор случайных чисел жил в агенте), карточка молчала о том, что
  последний анализ уже вне спецификации, а три «различающиеся» альтернативы
  отличались в третьем знаке. На метрику решений всё это почти не повлияло
  (пропуски 41 → 40 из 65), и так и должно быть: правки про корректность, а не
  про числа.
* **Имитационная среда с замкнутым контуром** (`scripts/run_simulation.py`):
  рекомендации применяются, процесс отвечает, система видит последствия своего
  совета. Последнее долго было неправдой, и это главная находка последнего захода:
  модель качества в имитации читала признаки из истории, подставленные 2 и 15 мг/кг
  давали одно и то же решение, и система давила, не зная, что уже снизила серу, —
  отсюда прежние «сера 2.6 при пределе 10» и «режим в упор дрейфа». С замкнутым
  контуром на июньском окне — 5 небольших вмешательств вместо 25, все четыре шага
  с превышением убраны. Если процесс отвечает на температуру втрое слабее, чем
  думает система, контур компенсирует это числом шагов (11–13) и снова убирает все
  превышения. Разбор — `docs/HARD_CHECKS.md` §10. Насыщение запаса по качеству и
  подавление воздействия, найденные раньше, остаются: в разомкнутом прогоне по
  тестовому периоду движение уставок за полгода упало с 227 до 40 °C при тех же
  пропусках и ложных тревогах.
* **Сравнение архитектур в числах** (`scripts/compare_architectures.py`) — ответ
  на вопрос «зачем вам четыре агента». Одноагентная система двигает уставки в
  **21 раз** больше (810 °C против 38.2 за полгода) при практически одинаковой доле
  ложных тревог. Агент надёжности не ловит превышений вовсе: он экономит пятую
  часть нагрузки на оборудование при в точности том же качестве. Аргумент здесь
  именно **цена вмешательства, а не полнота**: отношение 21× держится во всех трёх
  пересборках матрицы, а разница по пропускам между ними дважды меняла знак и
  установленной считаться не может. Разбор — `docs/HARD_CHECKS.md` §6–7.

## Закрытый контур

Организаторы назвали критерием оценки запуск в закрытой среде: технологическая сеть
предприятия с интернетом не связана. Система к этому готова по построению и
проверена запуском, а не только чтением кода:

* **во время работы в сеть не ходит ничего.** Внешних API нет, LLM не используется:
  объяснения собираются шаблонами из структур агентов, поэтому числа в карточке
  оператора не могут быть выдуманы. Модели обучаются локально на CPU,
  детерминированно, и в git не хранятся;
* **проверка запуском.** Цикл решения и импорт всех модулей идут внутри запрета на
  сетевые соединения (`src/nefte/offline.py`): любая попытка разрешить внешнее имя
  или открыть соединение наружу падает с адресом в сообщении. Локальные адреса
  разрешены — дашборд и внутренняя LLM живут в своей сети;
* **дашборд** не отправляет Streamlit статистику использования
  (`.streamlit/config.toml`).

```bash
pytest -q tests/test_runs_offline.py   # синтетический срез, все модули
python scripts/check_offline.py        # выданные данные и обученные модели
```

Установка зависимостей без сети — через заранее собранный каталог колёс на машине
с доступом в интернет и той же версией Python:

```bash
pip download -r requirements.txt -d wheelhouse
```

```bash
pip install --no-index --find-links wheelhouse -r requirements.txt
```

Внутри сети предприятия есть локальная LLM с OpenAI-совместимым API (модели до
~30 млрд параметров). Если её подключать к формулировкам, то только так, как
записано в `docs/PLAN.md`: числа берутся из структур агентов, модель лишь
переформулирует текст.

## Допущения

Все допущения собраны в `docs/DATA_NOTES.md` §5 и помечены в `configs/config.yaml`
ключом `assumption: true`. Коротко: рабочие диапазоны уставок, пределы качества
кроме серы, стоимостной прокси, прокси тяжести режима и модель блендинга — наши,
а не выданные организаторами.
