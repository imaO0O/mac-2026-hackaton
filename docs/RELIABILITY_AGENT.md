# Агент надёжности и достоверность данных

Участник 2. Всё на CPU, полный прогон бэктеста — около минуты.

```bash
python scripts/backtest_reliability.py
```

## 1. Достоверность данных: детекторы вместо ручных находок

Разовые наблюдения из `DATA_NOTES` переведены в код — `src/nefte/data/validity.py`.
Маски брака считаются один раз на всю историю, дальше срез на любой момент
отдаётся мгновенно вместе с причиной по каждому тегу. Именно эта причина попадает
в объяснение оператору, а не абстрактное «данные плохие».

| Детектор | Что ловит |
|---|---|
| Заглушки 307 / 313 | значение системы сбора, а не физическая величина |
| Мёртвый тег | ≤ 2 уникальных значения и больше половины заглушек |
| «Полка» | сигнал не менялся ≥ 3 часов подряд |
| Отрицательный расход | расходный тег ушёл в минус |
| Отказ анализатора | ПАК завис дольше порога — отдельное событие, не «шум» |

Результат по всей истории:

| Установка | Тегов | Мёртвых | Подозрительных по знаку | Средний брак |
|---|---|---|---|---|
| ЭЛОУ-АВТ-6 | 71 | 1 (`D10`) | 3 | 3.97 % |
| 24-2000 | 26 | 0 | 1 | 2.47 % |

Худшие теги АВТ: `D10` — 100 % (плотность нефти, сигнала нет вовсе), `F26` — 40 %
(пар в К-6: заглушки плюс полка на 440 суток), `T39` — 9.6 %. По 24-2000:
`Q20` — 11.7 %, `T18` — 6.7 %.

**Про отрицательные расходы отдельно.** Нельзя брать теги на букву `F`: для
24-2000 буква имени не соответствует смыслу. Нельзя и слепо верить описанию: у
`F5` описание говорит «расход пара», а 90 % значений отрицательные. Поэтому тег
считается принципиально неотрицательным, только если описание говорит о расходе
**и** доля отрицательных значений мала. `F5` (90 %), `F26` (60 %), `F63` (6 %) и
`F1` на 24-2000 (5 %) не «чинятся», а помечаются подозрительными: это сигнал
другой природы либо датчик с обратным знаком, и решать должен технолог. Такие
теги нельзя молча обнулять — это подмена данных.

**Отказы поточного анализатора серы:** 42 эпизода, 2299 часов суммарно — это
7.3 % всего времени. Три худших:

| Начало | Значение | Длительность |
|---|---|---|
| 2024-03-16 | 7.71 | 1122 ч |
| 2026-06-18 | 7.88 | 437 ч |
| 2026-04-15 | **18.45** | 289 ч |

Третий эпизод — демонстрационный: 12 суток прибор показывает грубое нарушение
спецификации, а лаборатория в это же время даёт медиану 3.4 мг/кг. Система обязана
это распознать и отказаться от рекомендации, а не «спасать» несуществующее
нарушение.

## 2. Тяжесть режима

Прямой разметки отказов и наработки катализатора в пакете нет, поэтому severity —
прокси-индекс, и это объявлено допущением. Состав: WABT реакторного блока (вес
0.40), перепад давления на Р-202 (0.25), температура на выходе печи П-3 (0.15),
скорость изменения режима за час (0.20).

**Исправлена утечка:** нормировка факторов считалась по всей истории, то есть
severity 2026 года нормировался по данным 2026 года. Теперь квантили берутся
строго по обучающему периоду (`ReliabilityAgent.from_history`), тест
`test_severity_norms_use_train_period_only` это фиксирует.

Распределение по времени: мягкий режим 44.4 %, средний 49.4 %, тяжёлый 6.1 %.
Тяжёлый режим запрещает повышение реакторных температур, средний — ограничивает
шаг вверх одним градусом.

## 3. Главный результат бэктеста: цели конфликтуют

Проверка «предсказывает ли severity превышение спецификации в следующем анализе»:

| Выборка | ROC-AUC severity | ROC-AUC обратного индекса |
|---|---|---|
| train | 0.567 | 0.433 |
| test | **0.351** | **0.649** |

AUC 0.35 — это не «модель не работает». Это значит, что связь **обратная**:
превышения по сере случаются в моменты, когда режим МЯГЧЕ. Физически всё сходится:
ниже температура в реакторе — легче катализатору и печи, но хуже обессеривание.
Ровно этот конфликт ТЗ и требует разрешать в оркестраторе, и теперь он подтверждён
числом, а не декларацией.

Практические следствия:

1. **severity нельзя использовать как предиктор качества.** Отдельный индекс для
   отдельной цели: качество считает агент качества, тяжесть режима — агент
   надёжности, конфликт разрешает оркестратор.
2. Рекомендация «поднять температуру» почти всегда улучшает качество и ухудшает
   надёжность. Значит, ограничение агента надёжности — не формальность, а
   единственное, что удерживает систему от бесконечного повышения температуры.
3. Связь severity с ростом перепада давления на Р-202 (недельные средние):
   Spearman **+0.157** — слабая, но правильного знака. Как прокси дезактивации
   индекс держится, но это именно прокси.

## 4. Что осталось сделать

1. **Наработка от начала цикла.** В данных нет разметки остановов и замен
   катализатора, но их можно найти по длительным провалам расхода сырья —
   тогда появится честный «возраст катализатора» вместо косвенных признаков.
2. **Детектор аномалий режима** (многомерный, а не потеговый): сейчас каждый тег
   проверяется отдельно, поэтому нефизичное сочетание нормальных по отдельности
   значений не ловится. Квантильный детектор на CPU закрывает задачу; LSTM-
   автоэнкодер — улучшение для бесплатного GPU, если останется время.
3. **Пороги risk_class** (0.5 / 0.8) взяты как разумные и пока ничем не
   обоснованы — стоит привязать их к квантилям обучающего периода.
4. **Подозрительные теги** (`F5`, `F26`, `F63`, `F1`) нужно либо интерпретировать
   по технологическим материалам, либо исключить из признаков осознанно.
